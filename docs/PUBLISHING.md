# Publishing FiestaBoard for Apple TV

The app bundle ID is `com.fiestaboard.tv`. For a physical Apple TV or signed
archive, copy `Config/Signing.local.xcconfig.example` to
`Config/Signing.local.xcconfig`, then set `DEVELOPMENT_TEAM` to your Apple
Developer team ID. Run `xcodegen generate` and open `FiestaBoardTV.xcodeproj`.
The local file is ignored by Git and applies to both the app and Top Shelf
extension in Debug and Release. It survives project regeneration; choosing a
team only inside the generated Xcode project does not. Do not commit a team ID
or signing credentials. Select your paired Apple TV in Xcode and use Run;
Xcode's signed-in Apple account must have access to that team and its signing
certificate. The unsigned Release archive in
CI checks compilation and bundle assembly; it is not an App Store upload.

CI also retains `release-xcarchive` for seven days. Its `.tar.gz` preserves
executable permissions; extract it to inspect the unsigned archive. Use only
an archive from the intended commit after both required CI checks pass.

For the first internal TestFlight build, create the app record in App Store
Connect with bundle ID `com.fiestaboard.tv`. In Xcode, archive the Release
scheme using your configured team, validate the archive in Organizer, then
choose **Distribute App → TestFlight Internal Only**. Automatic distribution
signing requires access to that team in Xcode and its distribution certificates
or cloud-managed signing. Development profiles alone do not establish that
distribution signing works. Confirm both targets retain the App Group.

`Config/ExportOptions-TestFlight.plist` provides the equivalent command-line
upload options. Use it with `xcodebuild -exportArchive`, the validated archive
path, an export output directory, and `-allowProvisioningUpdates`. For an
unsigned CI archive, supply your team ID in a local copy of that plist.
The options allow Xcode to manage build numbers and restrict the upload to
internal testing; that build cannot later be submitted for public release.
After processing finishes, add the build to the intended internal tester group
in App Store Connect and verify that it is available in TestFlight.

Archive with a **tvOS 26 or newer SDK**. Apple rejects uploads built against
an older one, and the deployment target stays at 18.0 — the SDK you build
with and the OS you support are different numbers. CI asserts the SDK version
rather than pinning an Xcode by path, because a pinned path that does not
exist fails open.

The Top Shelf extension has bundle ID `com.fiestaboard.tv.topshelf`. Register
the App Group `group.com.fiestaboard.tv` for both bundle IDs in the Apple
Developer portal, then refresh their provisioning profiles. Both targets use
`Config/AppGroup.entitlements`. The extension reads a locally written
manifest of panel names and static board snapshots from `Library/Caches/TopShelf`
inside the group container; it does not receive the board address, the
board's contents, or the sign-in credential.

Use **FiestaBoard for Apple TV** as the App Store name and **Your panels, on
your TV** as the subtitle. App Review may reject the platform wording under
guideline 5.2.5. If it does, use **FiestaBoard** and keep the subtitle. That
listing name is a separate string from the bundle's `CFBundleDisplayName`,
which is **FiestaBoard** and stays that way: it is what sits under the
Home-screen icon, where 24 characters truncate, and Apple's guidelines keep
their word mark out of a product name.

Every Info.plist key lives in `project.yml`. Both `Info.plist` and
`TopShelf/Info.plist` are generated by XcodeGen and are not committed, so a
hand edit is reverted by the next `xcodegen generate` and never reaches a
build — **bump `project.yml` only**. `MARKETING_VERSION` and
`CURRENT_PROJECT_VERSION` there reach both plists through
`$(MARKETING_VERSION)` / `$(CURRENT_PROJECT_VERSION)`; the extension's version
must match the app's or the upload is rejected, which is why both targets name
the same variables. A second upload at the same build number comes back
ITMS-90062.

The app has no analytics or tracking. Requests and credentials go to the board
chosen by the user, which can be local or at a typed HTTPS address. With protocol
v1 TV sign-in enabled in the board's Account settings (default off), QR/manual
approval and direct password sign-in store only a revocable, 365-day TV credential
in device-only Keychain storage. Direct password entry is sent to that board once;
older or enrollment-disabled servers retain legacy Keychain password sign-in.
HTTP connections transmit passwords and bearer credentials without TLS. The board
address and display preferences use UserDefaults. Do not claim passwords never
leave the device. No credential or private activation code goes to Top Shelf.

Sign out/Forget remove local credentials immediately and attempt server self-revocation.
When offline, remove the TV remotely in Account → Signed-in devices; local removal
does not prove remote revocation. TV credentials allow panel viewing and the six
approved display fields; FiestaBot is unavailable with this scope. Disabling new
TV enrollment does not revoke existing credentials. Revoked/expired credentials
never replay an old password. The QR is generated locally with Core Image.

Before beta distribution, record physical iPhone/Android scanning, desktop code
entry, direct password sign-in, restart/revocation and the 24-hour soak against the
same server build. Simulator tests and an unsigned archive do not replace these
checks. See `docs/REVOCABLE-SIGN-IN.md`.

FiestaBot changes the data flow: the board forwards conversation and relevant
board content to its configured AI provider. Native chat history is held in app
memory and cleared by New chat, sign-out, or restart; the board/provider can
retain their own records. Siri dictation uses Apple's system keyboard settings.
The old blanket “no third parties” claim and automatic all-“No” App Privacy
answers no longer describe the feature. Before publishing, align the App Store
privacy answers and published policy with the actual provider and server data
handling. Keep this document, SettingsScreen.privacyBody, the network usage
text in project.yml, and the privacy manifest consistent. The manifest's
UserDefaults reason and no-tracking declaration still describe the native app;
no microphone permission or embedded AI SDK was added.

`Resources/PrivacyInfo.xcprivacy` is the privacy manifest and it is required:
the app reads and writes `UserDefaults` in four places, which is a
required-reason API, and Apple's rule covers first-party code and not only
third-party SDKs. Without the manifest the upload comes back ITMS-91053. The
declared reason is **`CA92.1`** — defaults readable only by this app — and it
is deliberately not `1C8F.1`: the App Group entitlement exists for the Top
Shelf snapshot container, and no `UserDefaults` suite is ever opened against
the group. If a store ever moves to the group suite, that reason moves with
it. Only the app target carries a manifest; the extension compiles
`ContentProvider.swift` and `TopShelfSnapshotStore.swift`, which touch no
required-reason API. A malformed or mis-phased manifest reads as absent and
fails identically, so after the first archive open Organizer → Generate
Privacy Report and confirm the UserDefaults declaration is listed.

Export compliance is answered by `ITSAppUsesNonExemptEncryption: false` in
`project.yml`. The only cryptography is Apple's own — CryptoKit SHA-256 for
cache filenames, and the Keychain — and both are exempt. Without the key every
build sits in App Store Connect flagged “Missing Compliance” and cannot be
submitted until someone answers the questionnaire by hand.

Before submitting, App Store Connect also wants three things that have
nothing to do with the build. A **Privacy Policy URL** is mandatory even
though every App Privacy answer is “No” — the URL is a separate requirement
from the answers, and the submission cannot be sent without one; the page it
points at is also what the app's Settings screen tells people to look for.
Complete the **age-rating questionnaire** (everything is “None” for this app;
it has no user-generated content, no web browsing — tvOS has no browser — and
no links out). Answer **Content Rights**: the app displays no third-party
content, and the only vendored asset is the Spline Sans Mono font, shipped
under the OFL.

A reviewer cannot connect to a board. The only ATS exception is
`NSAllowsLocalNetworking`, and every address discovery builds — along with
every bare host typed into the manual field — is cleartext HTTP, so a public
demo address in that form is killed by ATS before a packet leaves the
device; the reviewer sees “Couldn't reach…”, which is indistinguishable from
a board that is switched off. A typed `https://` address is the one form ATS
would let through, and there is no public board behind one to point at.
Either way, do not put a demo address in the review notes. Say plainly that
the app is a companion to a physical FiestaBoard, normally one on the same
local network, and carry the demonstration in the submission itself: a
**screen recording** of connect → sign-in → panels → viewer → settings. Also
provide current screenshots from a tvOS simulator and verify the layered app
icon and Top Shelf assets in the signed archive before upload.

Running unattended is the headline use case and tvOS does not support it as
well as it sounds. There is no auto-launch API: after a power cut the TV comes
back to the Home screen and stays there until somebody picks up the remote. A
wall-mounted board that must come back by itself needs the Apple TV to be
**supervised and locked to the app with an MDM Single App Mode payload**;
there is nothing the app can do from inside its own sandbox. Say so to anyone
installing one, before they mount the TV.

After local testing, measure the 45 × 18 animated board on real Apple TV
hardware. The simulator cannot establish the 60 fps performance checkpoint.
